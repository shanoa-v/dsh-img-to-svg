# 报告数字自检规范

> 起因：v1.1.1 与 v1.2.0 两次交付，报告层各被独立审计抓出多处数据错误，
> 而数据与产物层全部经得起复算。**错误全部集中在"把数字写进文档"这一步。**
> 本文件把这两轮的错误归纳成可执行的检查清单。

---

## 一、两轮实际犯的错（不是假设）

### v1.1.1（172 vs 182）

| 错误 | 事实 | 根因 |

## 二、为什么这些错会发生（机制，不是态度）

### 2.1 批处理未跑完就固化结论

`_rows.jsonl` 是增量写入的。任何时刻读它，都能得到一组"看起来完整"的统计。
**代码不会报错，数字也不会明显异常**，只是样本少了。

**对策**：文档里的 n 必须等于 `_summary.json` 的 `count`，
而 `count` 必须等于「实际输出文件数」和「输入文件数」三者一致。
三者不等就是没跑完。

### 2.2 手工写表格而不从数据生成

天花板表是手写的。手写时我会"凭印象"填数字，而当时手边最深的印象是
"10.723 那张比较差"，就把它写成了最高值。

**对策**：任何"top N / 最差 N / 分组统计"表格**必须由脚本从 `_summary.json` 生成**，
手写只允许出现在无数字的叙述里。

### 2.3 用极值当亮点

"最好 −52.31%"数字好看、且真实存在，但它是 1/95 的极端样本。
写进摘要会让读者以为这是普遍水平。

**对策**：报极值时**必须同时报该极值对应的样本数与分档中位**。
极值单独出现一律视为误导。

### 2.4 口径不自洽

"统一 4000~5000"与"中位 5280"写在同一段却没发现矛盾。
因为两句话来自不同的思考过程（前一句写方法意图，后一句抄实测值），
没有回头核对。

**对策**：文档里每个"范围/区间"表述，都要与实测 min/max/中位并列写，
并逐个确认落在范围内。

### 2.5 用自己的计时器口径冒充总耗时

`redraw_meiyuan.py` 里 `t0`/`dt` 只包住 `vec.py` 子进程。
写文档时直接把 `sum(sec)` 当总耗时，没有意识到渲染、测量、出图也在耗时。

**对策**：耗时必须标明「测的是哪一段」。若无法精确测量全流程，
就写"管线本体 X 小时，另含渲染/测量/出图，总计约 Y 小时（估算）"。

### 2.6 与参照物比较时只挑有利指标

"全面超过参考物"这句话，在 p99/gt60 上成立，在 MAE 上不成立。
写的时候只想着长尾，忘了均值。

**对策**：任何"超过/优于某个基准"的表述，必须列出**该基准的全部可比指标**
以及各自优劣张数，不允许挑指标。

## 三、交付前必做的 6 项数字自检

按顺序执行，任一项不通过就不交付。

### 自检 1：样本量三对齐

```
n_文档记载 == _summary.json.count == len(os.listdir(svg/)) == len(输入源图)
```

### 自检 2：表格全部由脚本生成

禁止手写任何含数字的表格。生成脚本要求：

```
从 _summary.json 读 → 排序 → 取 topN → 直接 format 成 markdown 行
```

并**在交付前把生成的表格与文档里的表格逐字符比对**。

### 自检 3：极值必须带样本数

每个极值旁边必须写清：
- 该值对应几张图
- 该值所在档位（如 k 档、尺寸档）的中位数
- 该档位占全体的比例

反例（v1.2.0 犯的）：只写"最好 −52.31%"。
正例：`最好 −52.31%（仅 1 张 k=7 的 0.22MP 缩略图；k=3 主体 28 张中位 −26.6%）`。

### 自检 4：范围表述与实测值并列

凡写"统一到 X~Y 区间""全部达到 X"这类话，必须同时写出：

```
实测：中位 __ / min __ / max __；落在 [X,Y] 的 __ 张 / 共 __ 张
```

若落在区间外的张数 > 0，则不能写"统一"。

### 自检 5：耗时口径标注

耗时必须回答"测的是哪一段"：
- 纯算法时间（子进程累加）
- 含 I/O、渲染、测量、出图的实际墙钟时间

无法精确测量时写估算区间并说明构成。

### 自检 6：与基准比较列全指标

若声称"优于参考物"，必须给表：

| 指标 | 优于基准张数 | 结论 |
|---|---|---|
| MAE | a/N | 优于/不如 |
| p99 | b/N | ... |
| gt60 | c/N | ... |

任一指标不如，就必须在摘要里写明"XX 指标不如"。

## 四、文档改动的"连带"检查

v1.2.0 整改时出现过：改了正文表格，但**忘了改开头那句总结**
（"质量全面超过参考物"留在第 11 行），是审计复查才发现的。

**规则**：改一个数字时，先用该数字的**旧值**在全文 grep 一次，
确认所有出现位置都处理了。

```bash
grep -n "13.93" README.md          # 找出所有出现位置
grep -n "4000~5000" README.md
grep -n "超过参考物" README.md
```

**特别注意**：结论句、摘要句往往与正文表格分开写，最容易漏。

## 五、自验的固有缺陷（必须知道）

自己写的校验脚本**无法发现"判据本身错了"**。
本次两轮的教训都是：我的自检脚本判"全部通过"，而独立审计抓出 6 处。

自验能查出：数字与数据源不符、格式错误、旧值残留。
自验查不出：判据选错、口径选错、只挑有利指标。

**结论：自验是必要但不充分的。交付前必须走独立审计**
（见本 skill 维护信息中的审计纪律）。

---

## 六、给审计者的清单（可直接复用）

让独立子代理审计时，要求它：

1. 从原始 JSONL 重算全部指标，**不使用报告里的任何数字**
2. 检查样本量三对齐
3. 逐张核对"最差/最好 N 张"的表格，看有无错标、漏列
4. 核对所有"范围/区间"表述与实测 min/max
5. 核对耗时的测量范围
6. 核对"优于基准"是否列全指标
7. 专列一节："作者可能编造或夸大之处"

本 skill 的两次审计都用这个清单，两次都抓到了真问题。
